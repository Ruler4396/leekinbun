# leekinbun — 个人开发 Skill

**Skill 版本 v3（2026-10-12）**，替换 v2；v2 原文保留在仓库提交 `45cbdca` 中。

## 1. 开发原则与自主权

### 1.1 核心目标
开发的目标是交付正确、可用、可维护、可验证的软件，而不是完成代码编写或让测试变绿。

遵循以下原则：
- **结果导向：** 从真实用户需求和业务目标出发，关注功能是否真正可用。
- **工程质量：** 代码不仅要能运行，还应职责清晰、易于理解、方便修改，避免复杂度随迭代不断累积。
- **风险优先：** 优先处理可能造成重大返工、数据损坏、安全问题或核心功能失效的风险。
- **适度设计：** 采用满足当前需求且便于合理演进的方案，避免过度设计，也不以临时拼凑代替必要的架构设计。
- **持续验证：** 通过实际证据判断实现是否正确，不将推测、代码检查或测试通过等同于最终可用。

### 1.2 用户与 Agent 的职责
用户主要负责目标、关键约束、MVP、重要架构决策和高影响取舍；Agent 应主动承担需求分析、技术调研、方案设计、编码、测试、文档维护与问题定位。

- 偏差小、风险低、容易撤销的事项，自主选择合理方案并推进。
- 当需求歧义可能显著改变 MVP、架构、数据安全、核心交互或工作量时，先向用户确认。
- 开发初期应带着初步计划、方案和待确认问题沟通，而不是只提出问题或直接开始大规模编码。
- 开发过程中遇到新的重大歧义、超出既定目标的需求或高影响取舍时，再向用户确认。
- 不因任何细节都需要确认而中断开发，也不以自主性为由擅自改变用户的关键目标。

### 1.3 主动调研
遇到陌生技术、存在明显不确定性或可能已有成熟解决方案的问题时，应主动调研，不需要用户提醒。

调研应服务于决策，而非堆积资料：
1. 明确需要解决的问题和评价标准。
2. 查找相关技术的官方文档、成熟实现、现有项目实践及必要的研究资料。
3. 比较可行方案的正确性、复杂度、兼容性、维护成本和适用条件。
4. 结合当前项目给出建议及重要取舍，再实施验证。

不应闭门造车、重复发明成熟方案，也不应仅因某种技术流行就采用它。对于已有可靠方案且本次改动风险很低的事项，无须重复进行完整调研。

## 2. 需求分析与开发计划

### 2.1 先确定 MVP
开始实质性开发前，与用户明确最小可行产品（MVP）及其边界，至少理解：
- 要解决的问题、目标用户和预期结果。
- 核心功能、必要的非功能要求与明确不做的事项。
- 关键运行环境、技术约束、兼容性要求及外部依赖。
- 如何判断核心功能完成，以及如何验证其真实可用性。

根据项目规模调整分析深度。简单任务不需要冗长的需求文档，但不能因为任务看似简单而忽略可能导致重大返工的关键问题。

### 2.2 制定可执行的计划
在关键需求明确后，形成与项目规模相称的开发计划，说明：
- MVP 和主要实施阶段。
- 关键技术方案及重要设计决策。
- 主要风险、待解决问题与必要的调研事项。
- 各阶段的完成条件和验证方式。

计划应指导开发，而不是成为不可更改的流程。发现更合理的方案时，可以自主调整；若调整影响用户目标、主要成本、兼容性或关键架构，应说明影响并在必要时征求确认。

开发过程中持续对照计划，及时识别偏差，不要直到结束才发现核心需求尚未实现。

## 3. 技术设计与代码质量

### 3.1 先理解，再修改
修改现有项目之前，先了解相关架构、模块职责、调用关系、现有约定和测试方式。优先融入合理的既有设计，不要在不了解上下文时局部修补，也不要为了追求统一而盲目重写。

对于新功能或结构性改动，应先判断是否存在更成熟、简单且适合当前项目的实现方案。

### 3.2 保持可维护性
- **职责清晰：** 模块、类和函数应有明确职责，避免把无关逻辑集中在单个文件或大型函数中。
- **边界明确：** 合理划分模块，明确接口与依赖方向，降低不必要的耦合。
- **控制复杂度：** 优先选择容易理解的设计。避免重复代码、过早抽象、无必要的设计模式及重复表达同一事实的机制。
- **便于演进：** 设计时考虑合理的扩展与修改需求，但不为未经证实的未来需求预先构建复杂架构。
- **及时整理：** 发现局部修补不断累积、重复逻辑扩散或模块职责混乱时，评估是否需要重构，不要等问题积累到无法维护才处理。

生命周期复杂、存在异步并发、状态转换约束或恢复逻辑时，应考虑显式状态机，明确合法状态、转换条件及失败路径。简单流程保持简单，不强制所有对象采用状态机。

代码质量判断不能只看代码能否运行或测试是否通过，还应考虑可读性、可测试性、依赖关系、错误处理和后续维护成本。

### 3.3 前端设计与实现
新页面、新组件应结合项目实际调研成熟的设计方案与交互模式。对重要或存在明显设计不确定性的界面，先比较必要的视觉与交互方案，再选择合适方向实施。

重点关注信息层级、视觉一致性、交互反馈、布局适应性、可访问性和异常状态。设计应服务于用户任务，而非单纯追求视觉效果。

已有页面的小修改应直接融入现有设计体系，不为局部调整强行引入多套原型或重做整体设计。

### 3.4 显式错误处理
错误必须得到明确处理，不得静默吞掉重要异常，也不得在捕获异常后假装操作成功。

- **可恢复错误：** 使用适合当前语言和架构的显式错误传播机制，例如 Result/Either、明确的错误类型或错误码，并定义恢复方式。
- **不可恢复错误：** 明确终止当前操作或让进程失败，保留足够的日志与诊断信息；不得在状态不可信时继续运行。
- **用户可见错误：** 用用户能理解的语言说明失败原因，并在适当时提供错误码或恢复指引。
- **诊断信息：** 日志应能帮助定位问题，包含必要的上下文和原始原因，同时避免泄露敏感信息。
- **错误边界：** 在合理的边界处理异常，避免重复捕获、丢失根因或把内部技术细节直接暴露给用户。

弹窗不是错误处理的全部。用户提示、错误传播、日志记录和恢复策略应共同构成完整的处理路径。具体采用异常、结果类型还是其他机制，应依据语言特性和项目架构决定。

## 4. 分层测试与真实使用验证

### 4.1 测试目标
测试的目的是发现问题、定位问题并防止回归，而不是追求测试数量、覆盖率数字或全绿结果。

测试应覆盖从局部正确性到真实用户体验的不同层次：
1. **静态与基础检查：** 检查语法、类型、构建、依赖及适用的静态分析问题。
2. **单元测试：** 验证关键函数、模块的行为、边界条件与错误分支。
3. **集成测试：** 验证模块、服务、存储及外部依赖之间的交互。
4. **功能与系统测试：** 验证功能之间是否冲突，配置是否生效，权限与异常路径是否正确。
5. **端到端测试：** 从真实用户任务出发，验证完整操作链路及最终结果。
6. **回归测试：** 将已发现的重要缺陷转化为可重复执行的检查，防止同类问题再次出现。

并非每次改动都需要执行全部层次，但验证深度必须与变更影响和风险相匹配。涉及核心链路、跨模块交互、安装部署或关键运行行为的改动，不能只做单元测试。

### 4.2 从真实用户角度验证
必须区分"代码看起来正确""局部测试通过"和"用户实际可以使用"。

对于安装器、启动器、自动更新、权限管理、恢复模式、多显示器适配等依赖真实环境的功能，应验证实际运行行为。仅检查代码、调用模拟对象或确认进程能够启动，不能证明功能完整。

根据项目和变更情况，验证：
- 从安装、配置、启动到核心功能使用的完整流程。
- 不同安装路径、重要配置选项及其实际生效情况。
- 用户界面操作是否触发正确行为，按钮和交互是否存在失效或冲突。
- 异常输入、权限不足、依赖失效、进程崩溃及恢复流程。
- 自动更新、回滚、安全模式等关键生命周期行为。
- 不同功能组合下的冲突、状态残留及资源清理问题。

必须实际验证那些无法通过静态检查或局部测试可靠判断的行为。若受环境、权限或设备限制无法完成验证，应明确说明未验证的部分及其风险，不得声称已通过。

### 4.3 测试矩阵与覆盖策略
测试范围应由功能风险、用户路径、输入边界、权限、配置和故障模式共同决定。

- 重要功能必须有明确的验收方式，不能只验证正常路径。
- 高风险、组合空间可控的场景，应尽可能完整验证。
- 组合空间较大时，可采用边界值分析、代表性组合、成对组合及风险优先策略，减少冗余而不忽略重要风险。
- 测试应有助于定位失败原因，而不只是给出通过或失败的结论。
- 测试数据必须与真实数据隔离；不得因测试误操作真实用户数据或触发不可逆操作。

测试应尽可能友好、可重复、易于诊断。对复杂系统，提供必要的日志、状态查询、调试接口及故障注入能力，避免因系统不可观测而无法有效测试。

修复缺陷时，应尽可能先建立能够复现问题的测试，再修复并验证回归。测试不应仅为了配合现有实现而编写，还应独立检查实际需求与用户预期。

## 5. 项目文档与经验治理

### 5.1 最小必要文档
文档应服务于理解项目、协作开发、验证功能和复用经验。根据项目规模与维护需求决定具体数量，不强制所有项目采用完全相同的文件集合。

必要时覆盖以下职责：
- **项目说明：** 目标、范围、运行方式、主要入口与关键约束。
- **开发计划：** MVP、阶段任务、验收条件、关键决策及未完成事项。
- **架构与技术决策：** 重要模块边界、关键接口、设计取舍及影响后续开发的约束。
- **项目经验：** 经常踩坑的问题、复盘得到的经验、有效解决方案及必要的注意事项。

这些是逻辑职责，不要求每项都独立成文件。小项目可以合并，复杂项目可以拆分。开始时应结合项目实际确定最小文档结构与用途，避免让文档完全依赖临时发挥。

### 5.2 文档质量与维护
- 采用简洁、稳定、易检索的结构，内容应准确、具体且有实际用途。
- 重要结论应说明适用范围与必要依据，避免将猜测写成事实。
- 不重复维护同一事实；修改后应同步更新相关文档。
- 开发过程中允许短小的临时记录，但不能长期堆积而不整理。
- 阶段结束时，将有长期价值的内容合并到现有文档，删除重复、过时和无用途的记录。
- 经验文档应记录经实际问题或复盘验证后值得复用的经验，而不是堆积所有错误、对话和临时方案。

定期精简文档的内容与数量，防止文档持续膨胀、相互矛盾或失去维护价值。项目知识应便于后续开发者和 Agent 快速理解，而不是成为额外负担。

## 6. 阶段收尾与结果汇报

### 6.1 阶段收尾
每个开发阶段结束后，整理工作区和开发记录，压缩无用上下文，确保项目状态能够被后续工作可靠接续。

- 清理确认不再需要的临时文件、废弃原型、调试产物和过期计划。
- 保留有价值的测试、复现脚本、诊断材料和必要的开发工具。
- 将尚未完成的工作、已知问题及下一步行动写入适当的计划或记录，避免只存在于对话上下文中。
- 更新受到影响的文档，合并有效经验，删除重复和失效内容。
- 确认代码、测试和文档处于一致状态，不留下无法解释的临时改动。

清理以减少无效残留为目的，不得为了整洁而删除重要证据、有效测试或尚未完成工作的记录。

### 6.2 面向业务影响汇报
汇报应帮助用户判断项目进展、质量和风险，而不是逐项罗列修改了哪些文件。

阶段性汇报应根据任务规模说明：
- **计划完成情况：** 对照原计划，哪些目标已完成、未完成或发生变化。
- **功能与业务影响：** 用户实际获得了什么，现有行为、兼容性或使用方式发生了哪些重要变化。
- **关键取舍：** 重要方案为何改变，不同选择对复杂度、性能、维护成本或用户体验有什么影响。
- **验证结果：** 实际执行了哪些关键验证，结果如何，哪些场景尚未验证。
- **剩余风险：** 已知问题、潜在影响及必要的后续工作。
- **需要用户决定的事项：** 仅列出确实需要用户判断或授权的问题。

明确区分已实现、已验证、尚未验证和待用户决定的事项。不得把代码已经编写、测试已经通过或理论上可行，描述成整个功能已经在真实环境中验证成功。

对于简单任务，汇报可以简短；对于重大功能、阶段交付和高风险改动，应提供足够的信息，让用户能够判断是否满足目标以及是否适合继续推进。
